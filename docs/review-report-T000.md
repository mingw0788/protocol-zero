## 1. 审查结论

V1 的核心玩法闭环、胜负时间规则、主要状态、技术选型和分阶段交付方式整体合理。SRS 已为主要玩法建立可验证的规则，尤其是 270 秒生成 Boss、至少 300 秒且 Boss 已死亡才胜利、玩家死亡优先、暂停/升级期间冻结模拟、重复升级逐次选择等关键边界。

没有发现相互矛盾的已确认玩法规则，也没有发现需求完全没有任务映射的 FR/NFR 编号。但文档还不能视为完全可直接实现：部分关键数值和行为策略仍留给实现者推断；开发计划中的初始追踪矩阵有遗漏或任务范围偏差；T018 加入了 SRS 未要求的背景音乐；T001 的 Git 前提与当前目录状态不符。这些事项已记录在 docs/decisions.md，不会在本报告中替用户定案。

T000 已完成为文档审查任务。这不表示游戏已实现或通过运行验证。没有编写游戏代码、安装依赖、运行游戏测试或初始化 Git。T001 可在用户明确下达后进行工程初始化；受影响的玩法细节应在进入对应实现任务前确认。

## 2. 需求规格说明书审查

### 2.1 完整性与可验收性

SRS 已覆盖角色、地图、输入、敌人、武器、升级、Boss、波次、菜单、HUD、暂停、结算、本地记录、音效、非功能要求和交付验收。主要核心规则可以转成单元、集成和浏览器测试。

以下基线清晰且彼此一致：

- 有效战斗时间只在 PLAYING 增长；PAUSED、LEVEL_UP 和结算状态冻结模拟。
- Boss 在 270 秒达到时只生成一次；达到 300 秒且 Boss 已死亡才胜利；Boss 未死则继续；同一更新周期内玩家死亡优先。
- 斜向移动归一化；地图边界、相机边界和世界/屏幕坐标职责已区分。
- 敌人死亡、经验掉落、击杀计数、升级队列和重开清理都有防重复或隔离要求。
- 升级候选需去重、过滤满级项；不足三项显示剩余项；多级经验必须逐次完成选择。

### 2.2 遗漏、歧义和范围差异

1. **失焦行为未定。** SRS 允许切换标签页后自动暂停或冻结模拟，但两者的状态/UI/恢复行为不同。建议自动转入 PAUSED，返回页面后由玩家明确继续，且不补算失焦时间；该建议待确认，须在 T002 前落实。
2. **固定步长补帧策略不完整。** 已选 1/60 秒固定步长并要求限制异常 delta，但没有规定单帧最多补算步数、超额累计时间如何处理、切回标签页后如何清 accumulator。建议与失焦策略一起定义，避免长时间卡顿后补算大量战斗或生成事件；须在 T002 前落实。
3. **升级百分比公式仍是建议。** SRS 要求统一规则；SDD 给出按基础值乘以 1+n×每级百分比的建议公式，但明确允许 T000 审核，尚未成为已确认决策。建议统一采用对基础值线性叠加并明确舍入/上下限，须在 T012 前确认。
4. **若干战斗参数缺少可执行初值。** 脉冲枪射程、弹速/寿命、多重弹丸散布；轨道刃伤害、轨道半径/角速度/命中冷却；Boss 速度、接触/冲锋伤害、冲锋范围与冷却均未列出。SRS 将部分 Boss 属性写为“配置决定”，但未给首轮值或明确调优验收方法。建议保持既定玩法，仅由对应任务建立配置初值，并记录试玩调参原因；T008、T012/T013、T015 前需补齐。
5. **波次只有时间段，没有生成曲线。** 各波次的生成间隔/速率、敌人权重、是否随时间连续变化及达到 100 上限后的行为没有数值。建议由 T014 交付可配置的首轮曲线和边界行为，再通过试玩调整，不把参数写入渲染逻辑。
6. **T018 引入未登记范围。** SRS 只要求基础音效和音效控制；development-plan 的 T018 还要求背景音乐。建议在未批准扩展前，将背景音乐视为非 V1 要求，T018 先落实 SRS 所列音效与设置。
7. **本地成绩的统计口径不足。** “最高击杀”和“最佳通关成绩/最佳通关时间”未说明失败局是否更新击杀纪录、失败局能否产生通关记录，以及最佳时间是否记录胜利触发时的有效战斗时间。建议明确：击杀纪录取任意结束局的最高击杀，通关时间只在胜利时更新并记录胜利时有效时间；待确认后由 T019 实现。
8. **对象生命周期只有原则，没有上限策略。** 子弹、粒子有寿命/清理要求，普通敌人有 100 个活跃上限；经验晶体未说明未拾取时是否过期或是否设数量上限。长局且持续击杀时可能累积有效掉落物。建议在 T009/T020 明确晶体保留策略并测量，不擅自增加影响玩法的自动消失规则。
9. **性能/兼容验收缺少测试环境边界。** 60 FPS 被正确写为目标而非保证，但没有最低测试设备/分辨率、浏览器版本范围或“性能通过”的判据。建议 T020 记录测试设备、浏览器版本、分辨率、稳定 FPS/帧耗时和敌群负载；在没有测量依据前不把 60 FPS 写成硬性保证。
10. **满级保底选择可能没有实际效果。** 全部升级满级时提供生命恢复项，但满血时恢复量为零。现有规则仍然可执行，但未说明是否接受无效果选择。建议保持既定保底项，并明确其满血时的显示/选择语义；若要改为跳过或其他奖励，需先作为玩法变更确认。
11. **目标浏览器的“直接开局”需与交付方式对应。** SRS 表述为网页可直接打开，T021 要求静态托管。建议将验收解释为打开静态网页即可开始，不依赖账号、后端或开发服务器，并在 T021 验证部署产物。

上述事项多数不影响建立空白工程，但会影响 T002、T008、T012–T015、T018–T020 的实现和验收。具体确认状态见 docs/decisions.md。

## 3. 系统架构审查

### 3.1 合理之处

- 原生 JavaScript ES Modules、Canvas 2D、HTML/CSS、Vite、Vitest、Web Audio API、localStorage 与单机静态网页目标匹配；未引入后端、付费 API、重型框架或 ECS。
- 核心模拟与表现层分离，DOM 不作为战局状态来源；逻辑层负责伤害/升级，Canvas 负责绘制。
- 固定步长、有效游戏时钟、明确状态机、每局新建运行数据、配置只读共享和死亡幂等性，都直接回应了主要游戏风险。
- 先用朴素碰撞和活跃数量上限，再按实测考虑空间网格/对象池，符合 V1 的规模。
- 目标目录明确禁止 T000 提前创建游戏代码。

### 3.2 实施风险与建议

- **状态快照分配风险：** “Immutable/Read-only Game State Snapshot”应实现为只读视图/接口，不应每帧深拷贝整个世界；否则会增加垃圾回收压力。T002/T005/T020 的接口设计和性能审查需留意。
- **跨系统事件语义尚未定义：** 伤害、死亡、掉落、升级、状态迁移均提到事件/统一收尾，但事件所有权、处理时序和幂等边界留给实现。建议核心规则由一个权威系统处理，事件载荷保持小且明确，并按 SDD 的模拟顺序测试。
- **固定步长边界需落地：** RAF 渲染频率、模拟 accumulator、异常 delta 上限、后台恢复行为必须成套实现；不能只限制 RAF delta 后仍保留巨大 accumulator。
- **配置驱动不等于数值已定义：** 架构具备配置入口，但具体初始值及组合公式仍需对应任务补齐。不要在多个系统各自复制平衡常量。
- **性能结论只能实测：** 100 个敌人并不单独限定投射物/晶体/粒子总量；先按上限和生命周期实现，再以 T020 的实测决定是否引入空间分区或对象池。
- **T001 缺少版本控制前提：** 本次检查的项目目录下没有 Git 仓库，而 AGENTS 和计划要求任务提交、版本可追踪。建议 T001 在项目根目录建立仓库并创建忽略规则，确认生成的 lockfile 纳入跟踪；本轮未执行初始化。
- **入口路径容易放错：** 用户指定的工作目录 E:\AI\ProtocolZero_ReadyForCodex 只包含 protocol-zero 子目录。项目文档要求打开整个 protocol-zero 文件夹。后续工程文件应以 E:\AI\ProtocolZero_ReadyForCodex\protocol-zero 为项目根目录。
